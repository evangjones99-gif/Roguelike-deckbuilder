## New inherited finding: malformed settings suppress valid campaign loading

**P2 — `src/main.ts:52–58`.** Settings and campaign parsing share one outer `try`. Invalid settings JSON throws before the campaign is read; valid JSON `null` also throws at `value.mute`. On actual cdf production, a valid schema-3 seed57001 battle save plus settings text `null` or `{broken` resulted in **zero Resume controls**, notice **“Your save could not be read. A new campaign is still available.”**, unchanged exact campaign bytes and no uncaught page errors. The valid campaign is inaccessible in the UI until the preferences key is repaired; following the new-campaign suggestion can replace it. The same loading block is present in immutable v0.4, so this is inherited rather than introduced by world sampling.

The first diagnostic used a nonexistent `.title-screen` selector and timed out; the corrected probe waited for the actual new-campaign control and reproduced both cases. That harness mistake is not game evidence.

Immediate next-milestone repair: parse/validate preferences independently with defaults and an object/null guard, then always attempt campaign classification separately. Add actual UI regressions for both schemas with null and malformed preferences; preserve the campaign and truthful resume behavior. Development historical preservation may retain this explicit limitation; polished/commercial promotion must not.
