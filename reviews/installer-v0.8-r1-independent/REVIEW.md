# Independent Windows installer R1 source review

**Decision: reject activation of R1.** This is an independent static technical and isolation review of the frozen 15-file proposal in `frozen-r1`. No proposal script was imported or executed, no NSIS installer was built or launched, no workflow was dispatched, and no production file was changed. The three blockers below follow from the actual installed electron-builder 26.15.3 source and the proposal; they are not claims of a completed native Windows experiment.

The proposed gameplay payload is the already reviewed development build 0.7.0, runtime source digest `0be4f01d416e6fc4cca3f19b6916b5b65993b9fd426a926a1ede6d8487834a35`. That earlier executable/package evidence does not establish an installer pass. All 15 author inputs were independently copied, hashed, compared with the author manifest, and checked unchanged again for this report. Eight relevant installed stock-toolchain files are preserved with their hashes in `stock-source` and `stock-and-input-freeze.json`.

## Blocking findings

1. **The uninstaller-generation executable creates the real installation target before the smoke test.** `scripts/windows-installer-guards.mjs:48` emits an unconditional `customHeader` `InstallDir` pointing to the final QA installation. Stock `out/targets/nsis/NsisTarget.js:349` defines `BUILD_UNINSTALLER`, compiles the generator, and executes it at line 374. `out/vm/WineVm.js:28` runs that executable directly on Windows. Stock `templates/nsis/installer.nsi:45` inserts the same custom header, then `.onInit` executes `SetOutPath $INSTDIR` at line 52 before the `BUILD_UNINSTALLER` branch writes the uninstaller and exits at lines 63–65. This path creates the final target during packaging. The smoke test at `scripts/windows-installer-smoke.mjs:75` then refuses that preexisting target. Separate the generator directory from the actual installation using compile-time `BUILD_UNINSTALLER` handling and a fixed owned scratch path. Native compilation must subsequently verify both paths; deleting the target to hide this conflict would weaken the guard.

2. **The registry oracle rejects the two logical aliases of a correct per-user registration.** `windows-installer-smoke.mjs:47` queries both `Registry32` and `Registry64` for HKCU and HKLM; lines 91–94 require exactly one populated row, specifically HKCU/Registry64. Microsoft's primary documentation states that HKCU and HKCU\\SOFTWARE are shared: one physical key maps into each logical view, and subkeys inherit that behavior unless listed otherwise. The GUID installation and uninstall paths are not the documented Classes exceptions. A correct HKCU registration is therefore visible in both queried views. Validate consistent aliases of the same exact QA identity and installation path, with no HKLM registration; do not treat aliases as duplicate installations. The primary document is preserved as `microsoft-shared-registry-keys.md`, with successful GitHub fetch metadata. The failed direct Microsoft Learn fetch is also retained, rather than represented as a successful source read.

3. **The stock installer writes to the production-name updater cache outside the QA root.** The proposal changes appId, GUID, executable name and installation/profile directories, while retaining the accepted package's metadata name. Stock `out/appInfo.js:115` derives the name from package metadata and lines 123–127 derive its updater cache from that name. `NsisTarget.js:501` defines `APP_INSTALLER_STORE_FILE` for the embedded installer irrespective of the proposal's `differentialPackage:false`. Stock `templates/nsis/include/installer.nsh:88` extracts the package and line 93 copies the installer into `$LOCALAPPDATA\\${APP_INSTALLER_STORE_FILE}`; `include/installUtil.nsh:12` creates its parent and copies the file. With package name `hollowpact`, this targets `$LOCALAPPDATA\\hollowpact-updater\\installer.exe`, outside the isolated QA directory and potentially overwriting an existing cache. Redirect the stock compile-time cache destination to an exact owned QA child before the copy is expanded, and witness that the default cache remains unchanged across build, installation and uninstallation. Do not repair this by overwriting the accepted ASAR or restoring/deleting a production cache after the write.

## Further gates and observations

- **Incomplete uninstall oracle:** lines 147–153 check the executable, ASAR, registry, profile, staged package and sentinel. They do not verify all staged payload files or the remaining installation inventory. The generated `customRemoveFiles` recursively removes the guarded installation without checking removal errors; `_?=` runs the verified uninstaller in place. This static review does not assert which remnants will occur on Windows. It does establish that the oracle can report success with other payload remnants. Require a complete post-exit payload/directory inventory and bounded wait for normal self-removal, preserving any failure state rather than applying a generic cleanup.
- **Bounded artifact recovery remains open:** the workflow uploads one combined installer/evidence artifact. An actual installer is likely to exceed the connected download limit. A successful CI upload alone is not durable local preservation. Provide separate small evidence plus exact bounded parts, original executable hash/size and reconstruction metadata before accepting the native installer archive.
- **Other stock initialization writes:** `templates/nsis/multiUser.nsh:36` calls `SHGetKnownFolderPath` with `KF_FLAG_CREATE` for UserProgramFiles before the final `/D` override at lines 50–53. This can create the default Programs directory outside the QA root. Review compile-time suppression or qualify and witness this scope. This is an observation about potential directory creation, not evidence of an existing file being overwritten.

The proposal has useful source-level protections: pinned actions, read-only workflow permissions, no PR trigger or persisted checkout credentials, exact branch/repository/source checks, no publishing/signing credentials, a random QA identity, strict path validation and ancestor link checks, fresh directories and ownership/sentinel checks, no elevation helper, no shortcuts or automatic game launch, and preserved failure state. The smoke harness also plans exact payload checks, local canonical gameplay, persistence and optional synthetic feedback. These protections do not resolve the stock-code blockers above or constitute native execution evidence.

## Required fresh review

Keep R1 and this rejection frozen. Review a separately frozen R2 with exact source hashes, stock expansion ordering and generator/cache path distinctions, shared-registry alias checks, complete uninstall inventory, and bounded evidence transport. Only after independent source acceptance should the owner-approved native workflow compile and exercise the installer; inspect actual build, installed renderer, native uninstall, registry, cache/profile/sentinel preservation, original installer resources/signature and bounded archive receipts. A successful isolated QA identity would still not prove production-identity upgrades, migration from an existing consumer profile, SmartScreen trust, signing, Steam integration or publication. No AAA or human-fun claim is made by this review.

Primary reference: <https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/WinProg64/shared-registry-keys.md>. Source evidence and fetch failures are retained alongside this report. The independent reviewer wrote only this exterior review directory; the author proposal, production files and earlier archives/reports were left intact.
